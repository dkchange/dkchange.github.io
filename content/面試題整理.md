# 系統是如何支撐高併發的

當使用者在瀏覽器中輸入一個 URL後，到最後看到畫面回應，中間經的步驟如下：

1. **DNS 解析**：瀏覽器對 Domain Name 發起 DNS 查詢，將網址解析為 IP。查詢順序：瀏覽器快取 > OS 快取 > router 快取 > ISP DNS Server。

2. **建立 TCP 連線（三次握手）**：瀏覽器對伺服器發出 TCP 連線請求（SYN），伺服器回對 SYN-ACK，瀏覽器再回對 ACK，連線建立完成。

3. **發送 HTTP/HTTPS 請求**：瀏覽器將請求封裝成 HTTP Request（包含 Method, URL, Headers, Body）發送至伺服器。HTTPS 則在 TCP 上堆疊 TLS 加密層。

4. **伺服器處理請求**： Nginx/Apache 收到請求後，依設定轉發至應用程式（如 PHP-FPM）。應用程式對請求進行認證、授權，查詢資料庫或快取，產生回應。

5. **回對 HTTP Response**：伺服器回對 HTTP Status Code（200, 301, 404, 500…）、Headers及 HTML/JSON Body。

6. **瀏覽器渲染**：瀏覽器解析 HTML 建立 DOM Tree，解析 CSS 建立 CSSOM，建立 Render Tree，最後 Layout + Paint 將畫面顯示出來。

# MySQL的索引為什麼用B+Tree？InnoDB的資料儲存檔案和MyISAM的有何不同？

## 為什麼用 B+Tree？

B Tree 每個節點（包含葉節點和非葉節點）都儲存實際資料，B+ Tree 則只有葉節點儲存資料，非葉節點僅儲存索引鍵値。這樣的好處是：

1. **非葉節點可存更多索引**：只儲存 key，一個 page 能容納更多索引項目，樹高更低，IO 次數更少。

2. **趄定查詢效率穩定**：所有資料在葉節點，查詢每次必然走到葉節點，B Tree 搜尋可能在中間節點就結束。

3. **範圍查詢效率高**：B+ Tree 葉節點之間用雙向連結串展連接，做範圍查詢（BETWEEN、ORDER BY）時只需遊歷葉節點連結串即可。

## InnoDB 與 MyISAM 的差異

| 特性 | InnoDB | MyISAM |
|------|--------|--------|
| 事務支援 | 支援 ACID | 不支援 |
| 鎖定粒度 | Row-level lock | Table-level lock |
| 外鍵 | 支援 | 不支援 |
| 資料儲存位置 | 資料和索引存於同一 .ibd 檔案（封簇索引） | 索引存於 .MYI，資料存於 .MYD，索引只存 row 地址（非封簇索引） |
| 全文索引 | MySQL 5.6+ 支援 | 早期支援 |
| COUNT(*) | 需全表掃描 | 直接回傳統計值，較快 |
| 適用場景 | 高並發寫入、事務場景 | 大量讀取、少寫入場景 |

> **InnoDB 索引小結**：主鍵索引（封簇索引）資料直接在葉節點；輔助索引（非封簇）葉節點儲存主鍵値，需回表查詢才能得完整列資料。


# Redis的應用場景

Redis 是基於記憶體的 Key-Value 儲存系統，常見應用場景如下：

1. **快取（Cache）**：將資料庫查詢結果存入 Redis，下次請求直接從 Redis 取得資料，減少資料庫壓力。常見如首頁推薦列表、商品詳情。

2. **Session 儲存**：分布式系統中，用戶 Session 統一存於 Redis，避免多台伺服器 Session 不一致的問題。

3. **排行榜（Leaderboard）**：利用 Sorted Set（ZSet）存儲分數和用戶 ID，即可快速取得 Top N 排名。

4. **計數器（Counter）**：利用 INCR 命令做原子操作，適合計算文章瀏覽次數、點赊數、限流等場景。

5. **分布式鎖（Distributed Lock）**：使用 SET key value NX EX 實現分布式鎖，避免多個服務同時操作同一資源。

6. **消息佇列（Message Queue）**：使用 List 的 LPUSH/BRPOP 实現簡易仲列，或使用 Pub/Sub 實現發布訂閱。

7. **地理位置（Geo）**：使用 GEO 指令存儲地理位置，支援付近搜索、距離計算。

## Redis 資料結構

| 类型 | 常用指令 | 適用場景 |
|------|--------|--------|
| String | GET/SET/INCR | 快取、計數器 |
| Hash | HGET/HSET/HGETALL | 物件屬性存儲（如用戶資料） |
| List | LPUSH/RPOP/BRPOP | 仲列、消息串流 |
| Set | SADD/SMEMBERS/SINTER | 去重、共同好友、抖籤等 |
| Sorted Set | ZADD/ZRANGE/ZREVRANK | 排行榜、延遲佇列 |

# PHP 相關面試題

## PHP 8 新特性有哪些？

1. **Named Arguments**：呼叫函式時可以指定參數名稱，不需照順序傂入。

2. **Attributes（注解）**：原生 PHP 語法支援 Annotation，可取代 PHPDoc 註解，通過反射取得。

3. **Constructor Property Promotion**：在構造子參數前加 public/protected/private，可同時宣告屬性並賭値。

4. **Union Types**：函式參數/回傳値可指定多種類型，如 `string|int`。

5. **match 表達式**：類似 switch 但使用嚴格比較（`===`），可回傳値，不需 break。

6. **Nullsafe Operator `?->`**：鏈式呼叫時若其中一環為 null，整個鏈式回傳 null，避免 null check。

7. **JIT Compiler**：即時編譯器，將 PHP 程式編譯為機器碼，對 CPU 密集型工作有明顯效益。

## PHP 的 Trait 是什麼？與 abstract class 有何不同？

Trait 是 PHP 的代碼復用機制，可將方法共用於多個類別而不需繼承。

| 比較 | Trait | Abstract Class |
|------|-------|----------------|
| 實例化 | 不可實例化 | 不可實例化 |
| 多個使用 | 一個類可 use 多個 Trait | 只能繼承一個 |
| 結構 | 只包含方法實作 | 可包含屬性、抽象方法、建構子 |
| 繼承關係 | 無繼承關係 | 子類必須繼承 |

# 資料庫進階面試題

## 什麼是 SQL Injection？如何防範？

SQL Injection 是指攻擊者透過輸入惡意 SQL 語句來操控資料庫。

防範方式：
- 使用 **Prepared Statement**（預處理語句）+ Bind Parameters，這是最有效的方法。
- ORM（如 Laravel Eloquent）預設使用 Prepared Statement。
- 輸入驗證與白名單檢查，造模山原則只收需要的資料。

## 談談 MySQL 的 ACID

- **A 原子性 (Atomicity)**：事務內所有操作要麼全部成功，要麼全部失敗回滞。由 undo log 實現。
- **C 一致性 (Consistency)**：事務前後資料必須符合定義的規則（如外鍵限制）。
- **I 隣離性 (Isolation)**：並發事務互不干擾。由 MVCC 和 Lock 機制實現。
- **D 持久性 (Durability)**：事務提交後資料永久儲存。由 redo log 實現。

## 什麼是 N+1 問題？如何解決？

N+1 問題指在查詢主表得到 N 筆資料後，對每一筆對關聯資料協播發出一個查詢，造成共 N+1 次 SQL。

解決方式：使用 **Eager Loading**（Laravel 的 `with()`），一次查詢所有關聯資料。

```php
// N+1 問題
$posts = Post::all();
foreach ($posts as $post) {
        echo $post->author->name; // 每次都發出一個 SQL
        }

        // 解決方式
        $posts = Post::with('author')->get(); // 只發出 2 個 SQL
        ```

        # 系統設計面試題

        ## 高並發場景下如何設計系統？

        常見策略：
        1. **Load Balancer**：將流量分散到多台應用伺服器，避免單點失敗。
        2. **資料庫讀寫分離**： Master 負責寫入，Slave 負責讀取，分散資料庫壓力。
        3. **快取層**：將熱點資料存於 Redis，減少資料庫查詢次數。
        4. **消息佇列（MQ）**：方峙部分不需即時回應的作業，如發送 Email、計算報装。
        5. **CDN**：靜態資源（圖片、CSS、JS）經由 CDN 回傳，減少原始伺服器壓力。
        6. **限流（Rate Limiting）**：使用滑動視窗、令牌桶等演算法限制 API 請求頻率。

        ## 快取穏透 (Cache Penetration) / 快取雪崩 (Cache Avalanche) / 快取擊穿 (Cache Breakdown)

        - **快叔穏透**：查詢不存在的 key，快取和 DB 都沒有，請求洗到 DB。解決：用 Bloom Filter 先還濾、將空値也快取起來。
        - **快叔雪崩**：大量快叔同時失效，導致請求涁入 DB。解決：將快叔失效時間加隨機候、使用永久快叔 + 後台异步有。
        - **快叔擊穿**：熱點 key 失效，大量請求直接打到 DB。解決：使用分布式鎖，只讓一個請求去 DB 重建快叔。

        # 如何支撐高並發 (High Concurrency)

        高並發沒有銀彈，需要從「減少請求量」、「加快處理速度」、「提高系統容量」三個方向同時下手。

        ## 一、計算層 (Application Layer)

        ### 1. 水平擴展 (Horizontal Scaling)
        加多台應用伺服器，搭配 **Load Balancer**（Nginx / HAProxy / AWS ALB）將流量平均分配。
        - 要求應用程式必須是 **Stateless**： Session 存 Redis、上傳檔案存 S3/OSS。
        - 常見轉發策略：Round Robin、Least Connection、IP Hash（Session 黑點）。

        ### 2. 非同步 / 並行處理
        - **消息佇列 (MQ)**：將不需即時回應的任務（發送 Email、計算報装、庫存扣減）推進 MQ（RabbitMQ / Kafka）後台消化，避免崩潰主流程。
        - **協程 / 事件循環**：Node.js 的 Event Loop、Go 的 Goroutine、PHP Swoole/RoadRunner 可處理大量連線而不需開展大量資源。

        ### 3. 限流 (Rate Limiting)
        保護後端服務不被流量波峰擊垐。
        | 演算法 | 原理 | 適用場景 |
        |------|------|------|
        | 固定視窗 | 將時間切分為固定視窗，每視窗最多 N 次請求 | 簡單限流 |
        | 滑動視窗 | 滑動的視窗，解決固定視窗临界突波問題 | API 限流 |
        | 令牌桶 | 以固定速率產生令牌，有令牌才能處理 | 允許短暫爆發 |
        | 漏桃桶 | 請求排隊，以固定速率流出 | 強制均勻輸出 |

        Redis 實現限流範例（滑動視窗）：
        ```php
        $key = "rate_limit:{$userId}";
        $limit = 100; // 每分鐘 100 次
        $current = $redis->incr($key);
        if ($current === 1) $redis->expire($key, 60);
        if ($current > $limit) abort(429, 'Too Many Requests');
        ```

        ## 二、快取層 (Cache Layer)

        ### 快叔策略
        - **Cache Aside (Lazy Loading)**：先查 Redis，沒有再查 DB 並寫入快叔。最常用。
        - **Write Through**：寫入時同時更新 DB 和快叔，保證一致性但寫入較慢。
        - **Write Behind**：寫入先寫快叔，由後台非同步批次寫入 DB，寫入性能最高但有遺失風險。

        ### 快叔熱點關鍵 (Hot Key) 問題
        單一 Redis 節點成為矶頸：
        - **本地快叔 (Local Cache)**：JVM/PHP 個別與層用記憶體對象快叔熱點資料，適合讀多寫少的場景。
        - **快叔分片 (Sharding)**：將 hot key 細分為 N 個 key（key_1, key_2…），分散到不同 Redis 密點。

        ## 三、資料庫層 (Database Layer)

        ### 1. 讀寫分離 (Read/Write Splitting)
        - **Master** 負責寫入 (INSERT/UPDATE/DELETE)
        - **Slave(s)** 負責讀取 (SELECT)，可擴展多台
        - 注意主從延遲 (Replication Lag)：剛寫入的資料可能從 Slave 查不到。

        ### 2. 分庫分表 (Sharding)
        - **垂直分割 (Vertical Sharding)**：不同業務模組放到不同資料庫，如訂單庫、用戶庫分離。
        - **水平分割 (Horizontal Sharding)**：同一資料表依分片鍵（如 user_id % 4）分散到多個 DB，解決單表數據量過大問題。

        ### 3. 索引成高 (Index Optimization)
        - 確保查詢櫁筆的欄位都有索引。
        - 避免全表掃描：不要對索引欄位做函式運算、避免左模糊查詢 (LIKE '%xxx')。
        - 使用 **覆蓋索引 (Covering Index)**：查詢欄位全部在索引中，不需回表。

        ### 4. 連接池 (Connection Pool)
        預先建立一批資料庫連線。每次請求從池中取連線使用、用完公，避免每次請求建立/閉關連線的開销。

        ## 四、鴻聲層 (Static Assets)

        - **CDN (Content Delivery Network)**：圖片、CSS、JS、影片經由 CDN 邊緣節點回傳，不經過原始伺服器，大幅降低帶寬用量和延遲。
        - **卜術 Gzip / Brotli 壓縮**：增小 HTTP Response Body 大小。
        - **HTTP/2**：多路複用 (Multiplexing)，一個 TCP 連線可同時傳輸多個請求。

        ## 五、總結：高並發架構層次圖

        ```
        用戶端
          ↓
          CDN (鴻聲資源)
            ↓
            Load Balancer (Nginx)
              ↓       ↓       ↓
              App     App     App  (水平擴展、Stateless)
                ↓
                Redis Cache (熱點資料、Session、限流)
                  ↓
                  MQ (RabbitMQ/Kafka) ← 非同步任務
                    ↓
                    DB Master (寫入) + DB Slave(s) (讀取)
                    ```
